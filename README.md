# Spark SQL і DataFrame — демонстрація лекції 8

Готовий приклад для дисципліни «Системи високопродуктивних обчислень». Проєкт обробляє **синтетичний журнал Moodle**, відтворює числа з лекції та дозволяє переглянути фізичні плани. Даних реальних студентів немає.

## Швидкий запуск

Рекомендоване середовище: Linux, навчальний сервер або WSL2, **Java 17**, **Python 3.10–3.12**. Зафіксована залежність — **PySpark 3.5.7**. Локальний запуск використовує CPU однієї машини й не потребує окремого Hadoop-кластера.

З кореня проєкту:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
java -version
python src/moodle_demo.py --master 'local[2]' --mode small \
  --output outputs/small-01 --report-dir reports/small-01 --pause
```

Для наступного запуску використайте нові каталоги, наприклад `small-02`. Скрипт **не перезаписує** наявні результати. `JAVA_HOME` має вказувати на Java, якщо середовище не знаходить її автоматично. У WSL запускайте Python і Java всередині WSL.

Завершення без помилки означає, що перевірки пройшли. Наприкінці з’явиться:

```text
QUALITY: {"raw_rows": 10, "rejected_rows": 2, "duplicate_valid_rows": 1, "clean_rows": 7, "missing_course_rows": 0}
CHECKS: SQL/DataFrame and Parquet passed
```

Параметр `--pause` залишає застосунок активним. У браузері відкрийте адресу **Spark UI**, яку надрукує скрипт (у локальному режимі зазвичай `http://localhost:4040`). Натискання Enter завершує Spark. Без `--pause` програма закривається автоматично, а Spark UI перестає бути доступним. Текстові плани та JSON-звіт залишаються у `reports/small-01`.

## Малий набір та очікувані результати

У CSV є сім правильних унікальних подій, точна копія події 1, подія 8 без `user_id` та подія 9 із часом `bad`. Початково 10 рядків. Вилучення двох неприйнятних записів залишає 8, дедуплікація — **7**. Відхилені записи зберігаються окремо.

### Денні показники

| course_id | day | events | users |
| --- | --- | ---: | ---: |
| 10 | 2026-10-28 | 3 | 2 |
| 10 | 2026-10-29 | 1 | 1 |
| 20 | 2026-10-28 | 2 | 1 |
| 20 | 2026-10-29 | 1 | 1 |

Сума денних `users` не є кількістю унікальних користувачів за весь період. Користувач 101 присутній у двох днях. `COUNT(*)`, `COUNT(user_id)` та `COUNT(DISTINCT user_id)` для значень `[101, 101, NULL]` дають 3, 2 і 1 — цей випадок перевіряє окремий тест.

### Рейтинг та вікна

Курс 10: користувач 101 має 3 події, 102 — 1. Курс 20: користувач 103 має 2 події, 104 — 1. TOP 3 повертає по два наявні користувачі. Другий ключ `user_id` забезпечує однозначність нумерації за однакових значень активності.

Накопичувальні суми: для курсу 10 — 3 і 4, для курсу 20 — 2 і 3. `lag` означає попередній наявний рядок, а не обов’язково вчорашню календарну дату. Еталони збережено в `expected/`; малий режим автоматично звіряє з ними денні показники, рейтинг і тренд.

## Сценарій показу на занятті

1. Відкрити `data/small/events.csv`. Знайти копію, пропущеного користувача й некоректний час.
2. Запустити малий режим із `--pause`. Зіставити аудит і чотири денні рядки з таблицею вище.
3. Відкрити `src/moodle_demo.py`: функції `clean_events`, `daily_metrics`, `sql_metrics`, `rank_users`, `trends`.
4. У Spark UI переглянути SQL, Jobs, Stages, Executors і Storage. Знайти обміни й різницю між кількістю партицій та кількістю одночасних задач.
5. Відкрити `daily_plan.txt`, `window_plan.txt` і `parquet_pruning_plan.txt`. Знайти `Exchange`, сортування, агрегати, `PartitionFilters` та `ReadSchema`, якщо джерело їх показує.
6. Пояснити, чому 7 подій достатньо для перевірки логіки, але недостатньо для висновку про швидкодію.
7. Завершити малий режим Enter. Для демонстрації масштабу запустити великий режим окремо.

Код навмисно зібрано в одному Python-файлі, щоб переходити між функціями під час заняття.

## Масштабований синтетичний набір

```bash
python src/moodle_demo.py --master 'local[2]' --mode large \
  --rows 100000 --partitions 4 --hot-percent 80 \
  --output outputs/large-01 --report-dir reports/large-01 --pause
```

`--rows` — базова кількість до ін’єкції повторів. Повтор додається для кожної тисячної базової події, включно з першою. `user_id` відсутній для кожного 101-го індексу, час некоректний для кожного 211-го. Частина дефектів перетинається, а деякі повтори самі є дефектними. Аудит рахує відхилення перед дедуплікацією, тож його величини мають чіткий порядок обчислення.

Генератор використовує `spark.range` та вбудовані вирази й не створює великий список Python на Driver. Він детермінований: однакові параметри дають однакові записи. Початок часу — 28 жовтня 2026 UTC, значення секунд повторюються в 14-денному інтервалі. Для малого `--rows` набір може охоплювати лише частину цього інтервалу.

`--hot-percent 80` спрямовує 80% базових записів до курсу 10. Решта розподіляється між іншими курсами. Це властивість **до очищення**. Після вилучення дефектів точна частка може змінитися. Для порівняння використайте також 0 та 95. Не кожний оператор страждає від одного перекошеного ключа однаково: у денних агрегатах може допомогти часткове агрегування, а рейтинг має інший ключ групування.

На навчальному сервері почніть зі 100 000 рядків. Обсяг і кількість партицій змінюйте відповідно до виділених ресурсів. Після генерації застосунок виконує повні перевірки та кілька записів Parquet, тому його загальний час включає значно більше, ніж один SQL-запит.

## Контрольований експеримент зі стратегіями JOIN

```bash
python src/moodle_demo.py --master 'local[2]' --mode large \
  --rows 100000 --partitions 4 --hot-percent 80 \
  --benchmark --repeats 3 \
  --output outputs/benchmark-01 --report-dir reports/benchmark-01
```

Для ізоляції стратегій benchmark тимчасово вимикає AQE й автоматичний broadcast. Перша версія використовує `MERGE`-підказки, друга — явний `broadcast` малого довідника. Після експерименту попередні значення налаштувань відновлюються. Фактичні плани зберігаються: підтримка стратегії визначається ними, а не самою назвою підказки.

Вхідні сторони попередньо матеріалізуються в кеші. Результати порівнюються через двосторонній `exceptAll`. Для кожної стратегії є окремий прогрів, далі порядок чергується між повторами. Вимірюється **повний запис усіх колонок JOIN до Parquet**, а не лише побудова плану чи `count()`. Тому час містить витрати файлової системи. Кожна спроба має новий каталог.

`summary.json` містить кожне вимірювання, медіани й конфігурацію. Прискорення не гарантовано. Локальний режим демонструє роботу на одній машині. Для висновків щодо кластера потрібен запуск у відповідному середовищі та аналіз Spark UI. Якщо AQE увімкнено у звичайному ETL, його план може відрізнятися від цього спеціально контрольованого експерименту.

У прикладі немає вигаданих вимірювань. Цифри часу з’являються лише після реального запуску. Benchmark створює кілька повних копій результату (по одному прогріву та `--repeats` записів на стратегію), тому потребує додаткового дискового місця.

## Результати запуску

```text
outputs/<run>/
  events/day=.../       # очищені події
  daily/day=.../        # денні показники
  trend/day=.../        # lag та cumulative
  top3/                # рейтинг
  rejected/            # записи, які не пройшли перевірки
  benchmark/           # лише з --benchmark
reports/<run>/
  summary.json
  daily_plan.txt
  join_plan.txt
  window_plan.txt
  parquet_pruning_plan.txt
  benchmark_merge_plan.txt       # лише з --benchmark
  benchmark_broadcast_plan.txt   # лише з --benchmark
```

Рядки великих результатів не збираються на Driver. `collect()` застосовано лише до малих еталонних таблиць режиму small та агрегату за трьома типами подій. На екран виводиться до 12 рядків кожного результату. Сортування для попереднього перегляду також має вартість і не входить до окремих вимірювань JOIN.

Каталог `reports` завжди локальний для процесу Driver. Вихід `--output` підтримує шляхи Hadoop, зокрема HDFS. Якщо перевірка не проходить, програма завершується з помилкою. Частково записані виходи автоматично не видаляються: для наступної спроби потрібно нове ім’я.

## Запуск через YARN у лабораторному середовищі

Використовуйте вже встановлену на сервері сумісну версію Spark 3.5+. Не встановлюйте локальний `pyspark` поверх кластерного Spark без узгодження конфігурації. Для малого режиму CSV повинні бути доступні виконавцям, наприклад у HDFS. У командах нижче `STUDENT` замініть своїм дозволеним ім’ям каталогу.

```bash
hdfs dfs -mkdir -p /user/STUDENT/lecture8/input
hdfs dfs -put data/small/events.csv /user/STUDENT/lecture8/input/
hdfs dfs -put data/small/courses.csv /user/STUDENT/lecture8/input/
spark-submit --master yarn --deploy-mode client src/moodle_demo.py \
  --mode small --input-dir hdfs:///user/STUDENT/lecture8/input \
  --output hdfs:///user/STUDENT/lecture8/run-01 \
  --report-dir reports/yarn-01
```

`--master yarn` у цій команді належить `spark-submit`. Параметр `--master local[2]` застосунку тут не передають. Режим client залишає Driver на машині запуску, тому еталонні файли `expected/` та каталог звітів залишаються доступними. Для `cluster` потрібне додаткове поширення еталонних файлів — цей спосіб не налаштовано.

Для великого режиму файли CSV не потрібні: дані генеруються всередині Spark. Адресу Spark UI на YARN визначають конфігурація кластера та ResourceManager; `localhost:4040` не є універсальною адресою для всіх студентів. Значення ресурсів Executors і політики черги потрібно узгодити з лабораторним середовищем.

## Публікація у Git

Підготовлена версія може містити локальну історію Git. Архів для завантаження містить тільки файли проєкту, без середовища, великих результатів, звітів і каталогу `.git`.

Для нового порожнього репозиторію, створеного у своєму обліковому записі:

```bash
# Якщо проєкт розпаковано з ZIP і .git відсутній
git init -b main
git add .
git commit -m "Add Spark SQL lecture demonstration"
# URL замінити адресою свого порожнього репозиторію
git remote add origin https://github.com/OWNER/spark-sql-moodle-demo.git
git push -u origin main
```

Для наявного репозиторію узгодьте каталог і гілку, щоб не замінити його вміст. GitHub, GitLab та інший Git-сервер можуть зберігати цей самий проєкт. Правила доступу й ліцензію визначає власник репозиторію.
